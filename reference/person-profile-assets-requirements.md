## 实施映射

这是从当前生产 `TOOL_META`、`people/service.py`、`visual/` 与 `webui/people_api.py` 核对的实现索引，不重写原始需求。

| 阶段 | 现行生产入口与行为 | 与原设想的实施边界 |
| --- | --- | --- |
| A 统一身份 | `people.PersonService` 持久化人物 UUID、平台账号、多名称、可见范围与来源；`person_query` 只读解析和分页 | 同账号沿用身份，重名不合并；名称不是授权。兼容迁移保留旧引用，冲突账号需人工核查，不支持模型自行合并账号 |

| C 视觉闭环 | `visual_asset_manage` 提供 `create_character`、`stage`、`derive`、`activate`、`set_policy`、`revoke_consent`、`retire`；`image_generate.subjects` 编译受控修订与有序参考图 | 人格素材库按当前可见 subject／profile 手动共享，不消耗逐人物 grant。真实当轮来源可直接绑定明确可见主体为草稿；非维护者 `activate:true` 返回 `activation.confirmation_required`，不改 active／身份／claims。维护者启用 CAS、停用／删除、身份隐私与私有范围保持受控。生成完成仅内部回调，显式发送才外发；旧读图／发送与无法验证绑定的 legacy 队列不绕过来源状态及范围 |

### 当前契约补充

- 工具目标引用采用 `requester`、`persona`、`person_id`、`name` 等形式。手动共享和部署额度是独立控制；旧 manual grant 保留兼容但不限制当前可见素材的手动使用，`auto_candidate` 才要求明确有限 grant。普通工具不可增加部署额度。
- 非维护者也能把真实当轮附件／source asset 绑定到明确可见的主体为草稿，上传者与主体可不同。`activate:true` 不会替其启用，只返回 `data.activation={success:false,status:"confirmation_required",code:"permission_denied"}`；维护者仍以 `expected_revision` CAS 启用。新投稿不再创建 `unbound` 草稿，旧草稿不自动猜归属，可由显式 `assign_draft` 迁移。
- 启用使用 `expected_revision` 比较当前正式修订；冲突必须重新查询。当前普通工具的 JSON Schema 仅暴露整数预期；管理 API 对尚无正式修订的档案可显式传 `null`。生成候选不因生成完成而激活。
- `controller` 应设置为可信人物 UUID，不能拿称呼或平台账号冒充；人格资料与普通真人／OC 的控制边界按生产服务判定。
- `person_query` 的 `sections.visual` 增加 `drafts`：与修订摘要同构、不含 `refs`，最多 5 条；无 active／candidate 但有 draft 时 `state=draft_only`。投稿者可查询 `profile_id` 与 `revision` 交维护者启用。档案仍按当前会话过滤，维护者身份不自动扩大私聊／群范围；扩大人格 scope 仍需应用管理员。
- 内容哈希用于回溯受管素材：本地副本、内联 base64／data URI 与 URL 下载解析后的内容仍按来源状态及范围检查，不能借格式转换绕过。跨 subject 重用同字节／asset 保留原来源，原来源停用或删除阻断子引用；任意路径／URL 不可入库。共享使用不转移归属或控制权。
- `retention_days` 是持久设置，当前没有自动 TTL 到期清理任务。两步删除清理该人物视觉域的本地图片、关联修订描述、任务输入与 JSON 队列快照、引用链接，并脱敏相关审计，保留防重放／计费墓碑。身份、称呼、声明、原聊天和来源证据不在此范围，`retained` 明示保留项。未完成清理列入 `unresolved`；逻辑字段清空不是 SQLite 空闲页、WAL 或磁盘历史安全擦除，已提交上游的数据、平台消息及离线备份另行处理，不能假称全部彻底删除。
- 当前入口使用 `sirius_pulse/people/` 与 `sirius_pulse/visual/`；原正文的模块和表名是设计建议，不是要求另行创建平行系统。

### 尚未据此证明的事项

本文不列测试数，也不宣称全部 AT、真实双人图片一致性、真实外部网络／JWT 部署或多进程性能已通过。真实上游效果与费用、AMKR 实际模型路由、外部副本撤回和生产备份清理需要独立验证；不因 HTTP 成功、模型被调用或本地候选生成而推定成功。

## 1. 背景与目标

### 1.1 核心问题

用户提出“生成我和月白的合照”时，目前主要依赖聊天模型从上下文中的路径自行判断：谁是“我”、谁是“月白”、哪张三视图属于谁、是否需要补充文字设定。该方式存在以下问题：

1. 昵称、账号、人物身份与视觉形象未形成明确关联，重名或改名可能导致串人。
2. 人格知道自己的设定，不等于生图接口已经收到对应文字与参考图。
3. 用户、人格、原创角色的图片容易混放，文件名无法可靠证明归属。
4. 新成员不能自然地通过对话登记称呼、画像与形象；模型缺少受控查询入口。
5. 自动生成的三视图可能补造未展示细节，不能直接成为正式设计。
6. 多人合批、跨群并发、后台任务与中途修改可能造成身份或版本漂移。

### 1.2 产品目标

- **G1 稳定认人**：平台账号先绑定稳定 UUID，再关联名称、画像与资产；改名不换身份，重名不合并身份。
- **G2 自然交互**：人格按需询问称呼、主动 query、补充资料，不把聊天变成注册表单。
- **G3 可控维护**：用户可添加或修改自己的资料和形象；其他人只能在授权范围内操作。
- **G4 正确送图**：人物生图入口强制解析资产，自动组装说明与有序图片字节，不依赖模型手填正式路径。
- **G5 有限自动化**：在明确授权、次数预算与去重控制下，自动生成三视图候选，并长期保存。
- **G6 不扰动人格**：普通聊天不额外跑画像 LLM，不加载整个人物库，不改变五阶段主流水线职责。
- **G7 可追溯、可回滚**：能回答“谁提供了资料、谁批准了变更、此次接口实际用了哪些版本与图片”。

### 1.3 成功定义

验收时必须分别给出三类结论，不得混为一谈：

1. **身份正确性**：人物及操作者来自可验证的消息与账号绑定。
2. **输入正确性**：最终 prompt、参考图顺序、字节哈希与所选版本一致。
3. **生成效果**：人工抽检是否保持角色特征，单独报告模型能力与参考配方的表现。

前两项是程序性硬验收；第三项是效果评估。HTTP 成功或生成了一张图，不代表角色一致性达标。

### 2.2 首版完整范围

首版交付包含以下四个连续阶段，前置阶段可先独立上线，但不得提前宣称后续功能已完成：

| 阶段 | 范围 | 核心交付 |
| --- | --- | --- |
| A | 统一身份与来源 | UUID、精确账号绑定、多名称、原消息锚点与兼容映射 |
| B | 人物画像工具 | 只读查询、受控更新、来源与权限、自然询问 |
| C | 视觉资产与人物生图 | 原图入库、候选／正式版本、确定性参考集、编译与输入快照 |
| D | 自动三视图候选 | 显式授权、配额、异步派生、去重、撤权与版本冲突处理 |

### 2.3 不纳入首版

- 不引入图数据库、独立人物微服务、新向量数据库或第二套身份解析器。
- 不根据重名、头像相似或模型判断自动合并账号；跨账号验证合并另行设计。
- 不默认跨人格共享人物档案、记忆或图片，不建设全站公开人物目录。
- 不从普通聊天自动抓取所有图片建立人物画像，不做人脸识别或现实身份推断。
- 不让 AI 生成图自动覆盖正式形象；“自动启用生成版本”不进入首版。
- 不建设完整图库 WebUI；先提供工具闭环及最小管理能力，管理 UI 可后续迭代。
- 不重建生图队列、外发链路或 AMKR 路由；厂商、Key、真实模型和采样参数仍由 AMKR 管理。
- 不保证外部服务能够撤回已提交请求、删除其副本或退还费用。

## 3. 总体设计与术语

### 3.1 职责边界

```text
入站消息 → 统一身份解析 → 来源锚点 → 人格正常对话
                                      │ 按需调用
                    ┌─────────────────┴─────────────────┐
                    │                                   │
             person_query                         person_update
             只读聚合查询                         受控资料维护
                    │                                   │
                    └───────── 人物领域服务 ─────────────┘
                                  │
                         visual_asset_manage
                         登记／派生／启用／停用
                                  │
                         人物生图资产编译
                         身份、授权、版本、图序校验
                                  │
                  现有 image_generate 队列 → AMKR
                                  │
                      本地产物与内部回调，是否外发由 Agent 决定
```

“统一入口”指共用领域服务与同一数据真相，不要求所有操作使用一个 Tool Schema。身份解析扩展现有统一链路，不在工具里另造昵称到 UUID 的权威解析器。

### 3.2 关键术语

| 术语 | 定义 |
| --- | --- |
| 人物 `person_id` | 程序分配并持久化的 UUID；可表示人类、当前人格或显式登记的虚构角色 |
| 账号绑定 | 平台身份命名空间与账号原生 ID 到人物 UUID 的可信关联 |
| 名称 | 首选称呼、别名、平台显示名或历史称呼，不是身份认证凭据 |
| 操作者 actor | 此次操作真正由谁发起或授权；不是模型自报的 owner |
| 目标 subject | 资料或图像描述的是谁；可能不是上传者 |
| 控制者 controller | 被授权维护该人物或角色资料的人；不等于对素材著作权的法律认定 |
| 证据引用 `evidence_ref` | 框架提供的、可回查原始消息及作者的受控引用；不是模型随意写的消息 ID |
| 视觉档案 | 某人物的一组形象设计，可有多个版本与多个用途 |
| 视觉修订 `revision` | 提交后不可原地改写的形象快照；启用通过切换指针实现 |
| 参考集 `reference_set` | 某视觉修订用于生成的有序图片、用途及必需项 |
| 派生资产 | 从原图裁切或生成的三视图等；必须保留来源链 |
| 正式形象 | 经过有权者明确确认、允许按对应范围使用的修订 |
| 授权 grant | 对读取、修改、外部处理、生成消耗、启用或外发的限定许可 |

### 3.3 三条不可破坏的原则

1. **账号确定身份，名称用于称呼与候选检索，模型不生成或决定 UUID 归属。**
2. **原图先保存；派生结果是候选；启用正式版本需要明确授权。**
3. **模型 query 帮助理解，生图入口的强制编译保证输入；后者不能被前者替代。**

## 4. 统一身份与 UUID 需求

### 4.1 身份建立（ID-01）

- 首次遇到新账号时，由框架使用标准 UUID 实现分配 `person_id`，持久化后复用。
- 身份建立不等待用户回答名字；“不知道怎么称呼”不等于“不知道账号是谁”。
- 首版不同账号默认分配不同人物身份；同账号的并发首条消息不得产生多个 UUID。
- 平台账号精确匹配优先于所有名称匹配；未知账号不得因为昵称相同而返回另一个人的记录。
- 若当前接入没有可信账号信号，标记为未绑定或会话临时主体，不伪造稳定身份，不允许其执行正式自有档案变更。
- UUID 不参与角色扮演文本，不要求用户记住，不作为密码或权限凭证。

### 4.2 账号命名空间（ID-02）

权威键为“平台身份命名空间＋原生账号 ID”；只有平台的账号 ID 本身按租户隔离时才额外包含可信租户键。不得把实现类型 `adapter_type`、昵称或群号当成账号命名空间。

- 同一平台账号在同人格的不同群中应解析为同一人物，群内资料可有不同可见范围。
- `adapter_route_id` 用于证明消息来自哪条连接和定位原始消息，不因切换路由自动变成另一个人。
- 平台命名空间变更、账号解绑或合并均为管理操作，不能由普通模型调用自行实施。
- 当前人格的自我 UUID 在人格存储中持久化；目录改名或迁移不应重新生成。
- 人格自我不是会话里的新增人类 participant，不修改“一会话一个主 AI”的契约。
- 账号绑定关系由统一存储管理；旧 `identities` 字段是“平台 → 单账号”字典，不能承载同平台多个账号。首版不提供账号合并，未来支持时以绑定关系为真源，旧字段只作兼容投影，不能相互覆盖。

### 4.3 只读解析与指代（ID-03）

统一解析服务提供严格只读模式，找不到返回未找到，不注册用户，不使用模糊名称结果作为可写身份。

| 表达 | 解析规则 |
| --- | --- |
| `requester`／原请求中的“我” | 解析到被选定原消息的真实作者 |
| `persona`／原请求中明确指向当前人格的“你” | 解析到当前人格自我 UUID |
| UUID | 查权限范围内该人物；不得跳过授权 |
| 明确 @ 或消息作者引用 | 用平台元数据精确解析 |
| 名称 | 查询当前授权范围的候选；多个候选即歧义 |
| “他”“刚才那个人” | 有唯一且可验证的引用链才解析，否则询问 |

当前人格名称与人类同名时，裸名称也可能歧义；不得静默让人格名称覆盖其他候选。模型改写后的 prompt 中的“我”不能作为原始人称证据。

### 4.4 多人合批与来源锚点（ID-04）

- 框架为可操作的入站消息提供 `evidence_ref`，其内部包含或可索引：人格命名空间、平台来源、路由、会话、消息 ID、作者 UUID、时间和附件引用。
- 引用仅能指向当前授权消息集合；模型填写任意字符串、其他群消息或历史截图中的 ID 均不得成为授权证据。
- 修改称呼、登记本人形象、批准候选必须校验实际证据作者，而不是取合批第一条消息的 caller。
- **操作发起者与证据作者必须分别验证。**模型选中他人的历史消息，不等于获得那个人的操作权限；只能在该消息确属当前待处理请求，或有明确且仍有效的限定授权时执行。甲引用／转发乙说过的话，不能作为乙本次同意。
- 多人合批中每个受控操作锚定其真实待处理指令；不得先让模型任意选择作者，再据所选作者反向授予权限。
- 多人同批请求若无唯一任务来源，返回 `source_ambiguous`，不扣费、不写资料、不猜作者。
- 回复“用这版”必须能唯一关联到待确认变更及有权确认的人；有多份候选时要求选择。
- 后台事件不伪装成新的人类指令；续跑保留原授权范围，权限按执行时状态重新检查。

## 5. 名称与自然询问需求

### 5.1 多名称模型（NAME-01）

- 一个 UUID 可有多个名称；一个名称也可命中多个 UUID，名称不得设为跨人物唯一。
- 每一有效作用域最多一个首选称呼；建议优先级为当前群显式称呼覆盖 → 人格内本人首选称呼 → 平台显示名 → 中性称呼。
- 名称分别记录：文本、规范化检索值、类型、作用域、来源、创建者、状态以及是否允许用于日常称呼／检索。
- 规范化仅做确定性处理，例如 Unicode 规范化、去首尾空白、适当大小写折叠；相似度只能提供建议，不能据此写入或合并。
- “叫我阿雀”更新首选称呼；“Sparrived 也是我”可新增别名；均只针对证据作者。
- “别叫我旧称呼”停止将该名称用于日常称呼；是否还可作为内部历史检索词按用户要求与隐私策略决定。
- 历史称呼默认不注入普通聊天；审计保留不等于日常可展示。

### 5.2 自然询问（NAME-02）

- 身份已知但首选称呼未确认时，框架提供简短缺项提示，由人格在合适时自然询问。
- 不强制每位新成员注册，不阻塞回答，不为询问名字额外启动一次 LLM 请求。
- 未回答、拒绝回答或明确不希望询问时，不逐轮追问；记录有限的询问状态并遵守冷却。
- 不将引用、第三方介绍、角色扮演台词或“我朋友叫……”当作本人的名字声明。
- 无可靠自述时可暂用平台昵称，但标记为平台观察值，不升格为本人确认名称。

## 6. 人物画像与记忆需求

### 6.1 统一查询视图（PROFILE-01）

查询按需聚合已有用户资料、结构化名称、可追溯事实、关系与记忆结果、视觉概况。既有记忆仍保留在原系统，人物工具返回关联与摘要，不复制一份完整记忆库。

资料必须区分：

| 来源类型 | 可以如何使用 |
| --- | --- |
| 本人明确自述 `self_reported` | 可作为其表达的偏好或称呼使用，不等于客观验证 |
| 平台／可信配置 `platform`／`configured` | 标明可验证来源，仍受字段适用范围约束 |
| 第三方陈述 `third_party` | 保留提供者，不覆盖本人声明 |
| 模型推测 `inferred` | 单独标记为假设，不自动成为正式身份、权限或正式外观 |
| 无来源旧资料 `legacy_unknown` | 可提示需核实，不补造证据或置信度 |

禁止模型自评分数作为身份认证或启用依据。身份、角色权限、账号合并与外部处理授权必须由可验证信号决定。

### 6.2 更新与纠错（PROFILE-02）

- 支持提出资料补充、纠正、停用，记录原值、变更值、证据及生效范围。
- 本人的明确称呼、低风险偏好声明可直接按授权落库；推测及冲突内容作为待确认记录。
- “我不喜欢蓝色”不能只追加在旧的“喜欢蓝色”旁边继续随机召回，应标记更正／替代关系。
- 对方的自述可以更正其自述偏好，不能抹除与其冲突的可验证平台事实或审计。
- 不将人物画像更新写入权限标记；诸如“我是管理员”只能是未验证说法。
- 敏感资料不因模型认为有趣而主动收集；默认只记录与明确用途相关的必要信息。

### 6.3 查询预算与缺项（PROFILE-03）

- `sections` 按需选择 `names`、`claims`、`relationships`、`memories`、`visual`；本人或有管理权限者还可请求 `changes`、`consents`、`jobs` 查看有限的变更、授权与任务摘要，不向普通查询开放管理日志。
- 默认返回摘要，不返回整段原始聊天、图片字节、完整账号列表、密钥或服务器绝对路径。
- 查询结果分别表达“人物未找到”“人物存在但字段缺失”“字段因范围不可用”；对无权知晓人物存在性的请求，统一外显为不可访问或未找到，不泄露隐藏候选。
- 默认最多返回 5 个候选，超出时通过受控游标分页；禁止一次枚举全部人物。
- 默认文本预算建议为 1,500 个字符，单次模型文本上限不超过现有工具结果预算 6,000 个字符；应在字段层裁剪并返回完整结构，不截断 JSON。
- 普通对话不强制 query；确定性人物摘要仅按需注入，不能增加每轮全库扫描或自动视觉调用。

## 7. 拟议工具契约

### 7.1 读写分离（TOOL-01）

首版使用同一领域服务下的三个工具入口，复用既有生图与读图工具：

| 工具 | 职责 | 副作用与自主回合 |
| --- | --- | --- |
| `person_query` | 查人物候选、名称、资料和视觉概况 | `read_only`；可在自主回合按原有可见范围查询，不冒用上个用户权限 |
| `person_update` | 维护称呼、提出资料补充或纠正 | 保守标记 `external_write`；首版不在自主回合直接改正式资料 |
| `visual_asset_manage` | 登记素材、提交派生、启用／停用视觉版本 | `external_write`；首版普通模型自主回合不直接调用 |
| `image_generate`（扩展） | 人物创作与现有普通生图 | 沿用现有副作用门禁；人物分支增加强制编译 |
| `read_image`（扩展） | 看已授权资产或既有临时图片 | 支持受控资产句柄；不能绕过读取与模型处理授权 |

当前执行器按整个工具的 `side_effect` 授权，在读取 `action` 之前可能拒绝自主调用。因此不得把 query 和写入混在一个 `read_only` 工具，也不得为整个混合工具开启 `allowed_when_self_initiated`。

本需求不新增一个假定现有框架支持的 `local_write` 枚举；本地写入的分类先保守处理。未来若细化动作级能力，须单独评审全链路门禁。

### 7.2 查询输入与结果（TOOL-02）

拟议示例：

```json
{
  "target": {"ref": "requester", "evidence_ref": "ev_request_01"},
  "sections": ["names", "visual"],
  "detail": "summary"
}
```

`target` 必须是可判别的单一类型：`requester`、`persona`、`person_id`、`name` 或受控 `mention_ref`。例如 `{"ref": "person_id", "value": "8f6f0f42-44f6-4b31-9956-0631c115d637"}` 表示按 UUID 查询，`{"ref": "name", "value": "小白"}` 表示查名称候选。查名称返回候选，查 UUID 也要检查权限；不允许用模型自报 `scope` 扩大查询范围。

| 输入 | 规则 |
| --- | --- |
| `target` | 必填；一种主体引用，不接受互相冲突的多种身份键 |
| `sections` | 默认 `names` 与 `visual` 摘要；只返回请求且获准的部分 |
| `detail` | `summary` 或 `detail`；详细模式不绕过字段权限或文本上限 |
| `query` | 可选；查询某人相关经历／事实的检索词，不作为系统指令 |
| `cursor`／`limit` | 可选；受控分页，候选每页最多 5 个，游标绑定查询与可见范围 |

没有提供 `query` 时，记忆部分仅返回有限概况或可用性，不检索并灌入全部历史。

拟议成功结果示例：

```json
{
  "status": "found",
  "person_id": "8f6f0f42-44f6-4b31-9956-0631c115d637",
  "display_name": "临雀",
  "revision": 7,
  "sections": {
    "names": {"preferred": "临雀", "aliases": ["Sparrived"]},
    "visual": {
      "state": "active",
      "profile_id": "vp_01",
      "revision": 3,
      "reference_set_id": "rs_03"
    }
  },
  "missing_sections": [],
  "has_more": false
}
```

`status` 至少区分 `found`、`ambiguous`、`not_found_or_not_visible`。歧义结果只列当前可见候选及最低必要消歧信息，不展示隐藏账号或其他群资料。缺项不创建记录。

### 7.3 人物更新（TOOL-03）

首版动作：`set_names`、`propose_claim`、`correct_claim`、`retire_claim`、`confirm_change`。不提供模型可用的任意字段 PATCH、账号绑定、身份合并或管理权限修改动作。`set_names` 可显式设置首选、追加别名、停用指定旧称呼，不允许直接删除历史证据。

```json
{
  "action": "set_names",
  "target": {"ref": "requester", "evidence_ref": "ev_answer_02"},
  "preferred_name": "阿雀",
  "add_aliases": ["Sparrived"],
  "expected_revision": 7
}
```

- `expected_revision` 来自查询或当前可信摘要；不匹配返回冲突，不静默最后写入覆盖。
- 证据作者必须与自我更新目标相同；管理员更新需额外验证其可信角色。
- 人格提示词、模型参数中自报的 `is_developer`、`owner`、`actor` 均不能成为授权。
- 对同一证据、目标和规范化动作意图的重复调用应返回已处理的 `change_id`，不得重复添加别名或副作用。幂等键不能只有消息 ID：同一条明确指令包含 stage 与 activate 时，两个动作应各有记录，不互相吞掉。
- 工具结果返回实际更新字段与状态；需确认的草稿不得伪装成已启用。
- `propose_claim` 使用目标、内容、来源证据和范围；`correct_claim`／`retire_claim` 必须引用原记录 ID。`confirm_change` 必须指定 `change_id`、预期修订与新的本人／有权者确认来源，仅确认对应草稿，不扩大为其他字段或后续操作的同意。

### 7.4 视觉资产管理（TOOL-04）

首版动作及语义如下：

| 动作 | 输入重点 | 结果 |
| --- | --- | --- |
| `create_character` | 明确的角色登记指令、名称、操作者证据 | 程序创建虚构角色 UUID 并记录控制关系；不创建或合并人类账号 |
| `stage` | 目标、受控附件或已授权资产引用、说明、来源证据、基准修订 | 保存原图并建立草稿；不默认改变正式指针 |
| `derive` | 来源修订、固定配方、授权证据或有效预授权 | 提交后台任务，返回 `job_id`；仅生成候选 |
| `activate` | 候选修订、变更 ID、当前预期修订、确认来源 | 有权者明确确认后切换正式指针 |
| `set_policy` | 本人／控制者来源、目标、自动化模式、能力范围、有效期、预期修订 | 保存限定的素材使用／自动候选许可，返回授权摘要；不增加部署方额度 |
| `revoke_consent` | 本人／有权者来源、授权 ID 或明确能力范围 | 撤回对应许可并处理关联任务；撤回不要求先 query 才生效 |
| `retire` | 目标修订或资产、来源证据、影响范围 | 停用未来引用，按撤权规则处理队列 |

- 同一条明确指令可支持先 stage 再 activate，无须机械地追问两次，但每一步都要落盘和鉴权。
- 恢复旧形象等价于再次授权启用已有修订，不原地改写历史文件。
- 2026-10-30 起，普通成员可凭真实当轮附件／source asset 将图片直接绑定到明确可见主体的草稿；上传者与主体分别记录。不得直接登记为他人的正式形象；新投稿不再产生 unbound，旧草稿只经显式 `assign_draft` 迁移。
- 正式清单不接受模型自行拼出的任意路径。临时 URL／本地图片如要导入，应由受控导入分支完成校验与归属确认。
- `set_policy` 只记录有权者对其素材和角色的明确许可，不能凭模型 `mode=auto_candidate` 就启用，也不能修改 `is_developer` 或部署方预算。返回 `grant_id`、模式、对象、修订覆盖策略、能力、会话范围、到期时间及有效次数；关键约束缺失或含糊时要求补充，不默认为无限授权。
- 原始“以后可以自动补三视图”是否覆盖未来修订必须明确；默认只覆盖当前选定来源。`revoke_consent` 可随时关闭自动化或撤回单项能力，不擅自删除原图。
- 草稿必须归属明确主体，不能挂到猜测的人物目录；上传者不会因创建草稿获得目标维护权。维护者启用仍走 CAS；投稿后可通过 `visual.drafts` 查询 `profile_id` 与 `revision`，不含 `refs`。

### 7.5 人物生图输入（TOOL-05）

```json
{
  "prompt": "临雀在左，月白在右，两人在海边散步，夕阳，轻松自然",
  "source_ref": "ev_request_03",
  "subjects": [
    {"ref": "requester"},
    {"ref": "persona"}
  ],
  "reference_images": []
}
```

- `source_ref` 锚定本次创作请求，`requester` 由程序解析；`subjects` 中可引用 query 返回的 `person_id`。
- `subjects` 可选，保持现有仅 `prompt`／`reference_images` 调用兼容；人物创作工具说明应引导使用 `subjects`。
- 模型漏传主体时，程序不得宣称已保证身份输入；有可信人物任务计划时提示补齐。首版不以不可靠的 prompt 关键词扫描假装完全防漏。
- 显式选择视觉版本只能从当前可见 subject／profile 的可用修订中选取，不接受随意 owner/path 组合。
- `reference_images` 保留为临时场景／姿势等参考；正式人物身份图由编译器解析，不依赖模型手工抄写路径。

### 7.6 错误与恢复（TOOL-06）

| 错误码 | 含义与模型下一步 |
| --- | --- |
| `source_ambiguous`／`evidence_invalid` | 原消息或作者不明确／不可验证；询问或重新选择合法证据 |
| `subject_ambiguous` | 多个人物候选；要求明确选择，不自动建档 |
| `not_found_or_not_visible` | 不可访问或不存在；不泄露隐藏人物 |
| `permission_denied`／`consent_required` | 权限或授权不足；请求对应有权者确认 |
| `revision_conflict` | 已被别人或新回合修改；重新 query 后决定，不自动重放旧写入 |
| `required_asset_missing`／`asset_invalid` | 必需图丢失、损坏或不合法；修复或选择正式替代集 |
| `reference_limit_exceeded` | 合并后超限；选择另一参考集或减少非必需参考 |
| `quota_exceeded`／`already_pending` | 预算不足／已有同类任务；停止重复提交 |
| `cancelled_by_revocation`／`outcome_uncertain` | 已撤权／上游状态不明；不得自动重试付费操作 |

所有错误不得把内部路径、凭据或隐藏资料返回模型。失败与候选状态不得在自然语言中包装成“已正式记住／已经启用”。

## 8. 视觉资产与版本需求

### 8.1 归属与原图入库（ASSET-01）

- 人物、操作者、上传者、控制者分别保存；上传者不自动等于图中人物。
- 用户头像／自设可作为该人类人物的视觉档案；用户的其他 OC 以 `kind=character` 单独登记并由其控制，不替换本人身份。
- 人格视觉资产绑定当前人格自我 UUID，维护权来自可信配置，不因同名用户而转移。
- 原图立即复制至长期资产区后才宣布保存成功；聊天缓存、平台签名 URL、任务临时产物都不能作为唯一长期副本。
- 不需要先生成三视图才能保存资产；单张已确认原图可以直接用于人物生图。
- 入库验证真实格式、可解码性、非空、单图大小、像素上限及路径边界；拒绝把非图片文件当图片上传。
- 远程导入限制协议、地址范围、重定向及流式大小；默认不允许任意内网 URL、元数据地址或路径穿越。
- 原图只读保存，不拉伸、改写或覆盖；裁切图与规范化副本都记录为派生资产。

### 8.2 外观说明（ASSET-02）

至少区分：

1. `identity_description`：发色、五官、耳尾、标志物等身份特征。
2. `default_outfit`：默认服装与配饰。
3. `variant_notes`：特定版本差异与限制。
4. `inferred_details`：未展示、由 AI 补全或推测的部分。

本次明确换装可以覆盖默认服装，不自动改变身份特征；用户要求改变长期发型等应建立新形象版本。说明冲突要标出并询问，不将所有历史描述拼成互相矛盾的 prompt。

### 8.3 生命周期（ASSET-03）

```text
原图入库 → draft → candidate → active
                    │           │
                    └→ rejected └→ superseded / retired
```

- 明确授权的原图登记可以从草稿经确认直接成为 active；不强制生成。
- AI 生成结果完成后只成为 candidate；缺少人工确认时不得进入正式默认参考集。
- 同一人物可保留多个设计档案，但同一用途／作用域只能有一个默认指针。
- 不可变的是已提交修订内容；变动的是经过 CAS 校验的当前指针。
- 新修订启用后，旧修订仍可追溯；拒绝或停用状态不等同物理删除。
- 不可用的正式集必须明确报错；只有预先确认的有序替代参考集才可自动选用，不能临时猜图替代。

### 8.4 参考集（ASSET-04）

参考项记录：资产 ID、人物 UUID、视觉修订、用途 `identity/outfit/pose/style/scene`、视图、顺序、必需性及内容哈希。

- 默认只选当前 active 且已授权的参考集；候选必须通过明确“预览该候选”的任务才能使用。
- 当前生图工具总计最多 4 张、单张 20MB；正式人物图和附加图共用总额，不静默截断。
- 双人首选各一张经确认的合集或单张身份参考，效果应实测；不硬性声称三视图合集优于所有单视图。
- 可保存正／侧／背等独立视图供查看或其他配方；没有可靠布局信息时不盲目按三等分切图。
- 每个人物的最低必需参考均须保留。预算不够时可减少明确可选项，或让用户选择，不得丢掉某个人物。
- 相同字节可以用于存储校验，但内容相同不证明人物相同，不按图片哈希自动合并身份。

## 9. 人物生图编译需求

### 9.1 必经步骤（GEN-01）

人物分支在现有任务入队前执行以下编译，不要求模型额外调用一次 query 才能正确工作：

1. 校验来源、操作者、目标人物与原始人称。
2. 校验读取、向模型处理／上传、生成消耗等所需权限。
3. 为每个人物选择明确的 active 视觉修订或显式指定的候选预览版本。
4. 展开参考集，验证字节、大小、归属、总数及顺序。
5. 合成身份说明、默认服装、本次覆盖与“参考序号—人物”的映射。
6. 物化输入副本，记录最终 prompt 与哈希快照。
7. 按幂等键写入现有生图队列，返回“已提交”，不声称已经生成。

任何必需步骤失败则不提交外部生图。程序不得在必需参考缺失时静默降级成纯文生图。

### 9.2 编译输出与审计（GEN-02）

每次人物生图至少保存：

```text
job_id、request/source_ref、actor 与授权引用
人物 UUID 列表、视觉档案／修订、参考集 ID
每张参考图的序号、用途、人物映射、文件哈希
最终 prompt、配方版本、输入清单哈希
队列状态、外部提交边界、结果路径／哈希、回调与外发状态
```

接口仍发送 AMKR 任务名 `image_generate`、最终 prompt 与参考图字节。人物含义不进入 Provider 路由层；无需修改 AMKR 的厂商选择或真实模型配置。

### 9.3 快照与权限（GEN-03）

- 普通形象更新不改变已入队任务的输入；后台不能重新解释“我”或重新选最新图。若只是 superseded，旧修订仍可在原范围执行；retired／删除表示不再允许使用，则按下一条规则拦截。
- **快照固定不等于权限永久有效。**实际提交外部接口前重新校验主体／profile 可见性、会话范围、来源状态与部署额度；自动任务还要重验实际 grant。结果对外展示或发送前再次校验。
- 登记后原文件丢失与任务快照丢失分别检查；后台缺少任何必需副本时失败，不调用无参考分支。
- 尚未提交上游的撤权任务取消。已提交请求只能尽力取消，结果隔离，不自动启用或外发，并告知外部处理可能已发生。
- 不把未知上游结果当失败自动重试扣费；保留 `outcome_uncertain` 并由有权者决定。
- 提交与撤权必须有持久化竞争边界：撤权生效先于本地提交许可领取时，不得向上游发起请求；提交许可已领取的竞争窗口须继续尽力拦截，不能证明未发送时按可能已外传处理。记录许可领取、实际发送开始与撤权时间，不将检查权限后无保护的长等待称为“实时撤权”。

## 10. 自动三视图派生需求

### 10.1 自动化模式（AUTO-01）

首版只提供：

| 模式 | 行为 |
| --- | --- |
| `manual` | 用户明确要求且部署额度允许后提交生成；不要求逐人物 grant |
| `auto_candidate` | 在有效预授权、预算与去重检查通过后，自动补全候选，不改正式形象 |

推荐用户启用自动化时选择 `auto_candidate`；但**初装无授权状态按 manual 处理**，不能因模型判断“适合生成”就产生费用。`auto_activate` 不在首版范围。

### 10.2 触发条件与执行身份（AUTO-02）

- 目标人物归属明确，原图已入库，缺少适用参考集或有明确派生请求。
- 模型可提出“适合补三视图”的建议，但此建议不是授权或质量证明。
- 自动候选的有效授权分别覆盖：资产所有者／控制者通过明确有限 grant 允许外部处理；部署方或配额承担者允许消耗生成次数。手动生成不沿用此逐人物 grant 要求。
- 普通聊天回合可按授权提交；纯自主回合不得冒用最近用户身份调用外部写工具。
- 自动后台控制器通过同一领域服务执行已授权任务，只能处理 grant 限定的人物、来源修订与配方，不绕过通用鉴权、不放开整工具自主写权限。
- 首版不增加“让模型先打分是否值得生成”的额外强制 LLM 请求。

### 10.3 生成与质量边界（AUTO-03）

- 复用现有异步生图机制，保存任务用途 `turnaround_derive` 与来源版本。
- 单张图片看不到的背面、配饰或服装结构属于设计补全，生成后标记 `ai_generated` 及推测部分。
- 生成成功后做文件可读性、尺寸、内容哈希等机械检查；模型视觉检查可给出建议，但不能据此自动认定“正式正确”。
- 默认输出一张可审阅三视图合集；是否裁切必须依据明确布局并检查，不强制所有来源都可自动切图。
- 保存来源原图、生成候选、配方与最终 prompt；候选不是原始设计证据。
- 后续生成默认仍使用原始已确认参考，不自动反复以未确认候选为输入，避免形象漂移。

### 10.4 去重、限额与重试（AUTO-04）

- 幂等键至少包含人物、来源修订／哈希、派生类型与配方版本，同键执行中返回已有任务。
- 已完成且仍有效的同键候选不自动再生成；用户明确重做时才分配新 attempt 并消耗预算。
- 原子预占次数，失败／取消是否释放按外部提交边界与可验证结果决定；未知结果不返还后自动重试。
- 首版采用次数预算作为刚性上限；缺少可靠价格与用量数据时，不伪报精确金额或“保证不扣费”。
- AI 候选完成不触发下一轮自动补全；失败不无限重试，限额到达停止。
- 配额不足不阻塞正常聊天或原图登记。

### 10.5 中途更新（AUTO-05）

基于 v1 的任务执行期间用户启用了 v2，结果仍归属于 v1；返回“基于旧版本生成的候选”，不得覆盖 v2。启用需要以当前修订为预期值重新确认。若来源已撤权或停用，完成结果按撤权规则隔离。

## 11. 权限、隐私与删除

### 11.1 能力分离（AUTH-01）

至少分离以下能力；拥有其中一项不自动拥有其他项：

- 看人物摘要／看详细资料。
- 读取图片及将其送入聊天视觉模型。
- 修改名称、资料或视觉草稿。
- 向生成服务上传素材。
- 消耗部署方生成预算。
- 启用正式形象、停用或删除。
- 在指定群／私聊展示候选或成品。

用户明确的本次创作请求，可在已说明的服务处理策略下进行手动共享；“上传图片”“同意保存”“模型建议生成”本身不等于持续外传或无限付费授权。手动共享不依赖逐人物 grant，但操作来源、主体、范围与部署额度必须可追溯；自动候选仍须明确有限 grant。身份、资料隐私和正式启用的授权不因手动共享而取消。

### 11.2 角色规则（AUTH-02）

| 操作者 | 默认允许 | 默认禁止 |
| --- | --- | --- |
| 本人 | 维护自己的称呼、提交自有资料及形象、按策略确认与撤回 | 自报管理员、直接修改别人、突破部署方预算 |
| 其他普通成员 | 查当前可见摘要、提出带来源建议 | 覆盖他人正式资料、读取私有图、冒名批准 |
| 角色控制者 | 维护被显式授权角色 | 自动获得人类本人隐私资料 |
| 人格管理者 | 维护人格形象及部署政策，执行可审计管理操作 | 仅凭群管理身份默认获得所有人的私人资料 |
| 模型／后台控制器 | 在当前授权下提出建议、查资料、执行已批准任务 | 自行授予权限、合并身份、伪造同意 |

账号可信身份、应用管理权限与平台群管理员是不同概念。管理员维护也应记录角色与操作来源；默认不将群管理员视为所有人物的资产控制者。

### 11.3 作用域（AUTH-03）

- 数据默认隔离在当前人格；相同平台账号在其他人格中的档案不自动可见。
- 同人格可跨群识别同一账号，但私聊事实和仅某群可见图片不会因此跨群公开；维护者身份也不自动扩大 profile 范围。
- 默认新资料作用域不宽于来源会话；扩大为人格内共享需应用管理员明确操作。
- 当前用户管理器能查询到某用户，不代表其资料或图片在当前群已获授权。
- 自主回合使用人格自身基础可见范围，不能继承最后一次聊天者的私人权限。
- query 的数据只作为参考，不作为系统指令；图片文字及工具返回不能提升权限。

### 11.4 撤回、删除与留存（AUTH-04）

- 停用／撤权先阻止后续使用，并使待执行任务失效；随后处理引用、缓存及副本。
- 删除覆盖原图、派生资产、任务输入副本、查询缓存、可定位的模型侧记忆索引和派生链接，不因任务快照固定而保留可继续使用的副本。
- 正在执行的外部请求、已发送群消息、外部服务副本和离线备份有独立边界，须明确告知，不能声称全部撤回。
- 审计只保留必要最小记录；删除敏感内容后可保留脱敏操作标记，不把原始内容无限期塞入审计。
- 首版软停用可走有权者明确工具操作；物理删除使用单独确认的管理入口，不放进通用任意更新动作。
- 备份及保留期必须可配置、可说明；没有实现完整清理链前不得宣称满足彻底删除。

### 11.5 首版最小管理闭环（AUTH-05）

不要求完整图库页面，但必须有受控管理入口复用相同领域服务，提供：

1. 设置人格形象控制者、部署方生成总额度与保留策略；仅可信应用管理者可用，不经普通画像字段更新。
2. 本人用 `set_policy` 授予限定自动候选许可，`revoke_consent` 撤回实际绑定的旧 grant／自动任务；旧 manual grant 兼容保留但不限制手动共享，部署额度与素材许可分别持久化。
3. 查看本人或管理权限内的草稿／变更 ID、修订、授权摘要与任务状态；可通过 `person_query` 的对应详细章节查询，受相同分页与脱敏规则约束。
4. 物理删除先返回影响预览及一次性确认引用，再由有权者明确确认执行，输出本地已清理范围、未完成项、备份及外部处理边界。

上述管理能力必须进入阶段 C／D 的交付范围，不能以“后续再做 WebUI”为由省略授权建立、撤回或删除入口；具体路由或 CLI 名称在接口设计时确定。

## 12. 关键用户流程

### 12.1 首次交流与称呼登记（FLOW-01）

1. 新账号到达，框架原子建立 UUID，平台昵称仅作为观察值。
2. 人格正常回答，合适时询问“我该怎么称呼你？”；不强制等待。
3. 用户回答“叫我阿雀，Sparrived 也是我”。
4. 模型调用 `person_update`，以该回答的 `evidence_ref` 绑定作者。
5. 返回新修订，后续优先用阿雀；同名他人不会被合并。

### 12.2 登记与修改形象（FLOW-02）

1. 用户说“这张是我的形象，以后在本群画我用这个”。
2. 保存原图、声明、会话范围和作者 UUID，建立草稿。
3. 该语句可构成本次正式登记的确认；核对可用权限后启用。
4. 未允许自动派生时不自动扣费；原图已经可以用于生成。
5. 后续“改成短发，其他不变”创建新候选，用户确认后切换，旧版可追溯。

### 12.3 双人人物生图（FLOW-03）

1. 用户说“画我和月白在海边散步”。
2. 人格可 query 双方视觉概况；缺失则自然询问，不必重复索取已经保存的图片。
3. 提交双方主体与原请求锚点，编译器强制绑定 UUID 和参考集。
4. 正式图与文字实际进入请求，任务保存图序映射与哈希。
5. 后台回调产物，由 Agent 选择查看、继续加工或发送，不自动刷屏。

### 12.4 自动三视图与并发修改（FLOW-04）

1. 用户已明确开启某范围的 `auto_candidate`，部署方分配可用额度。
2. 模型建议补三视图或控制器发现满足规则的缺项。
3. 鉴权、去重和预算预占后后台生成，期间正常聊天不等它。
4. 用户中途启用新设计，旧任务结果仍绑定旧版。
5. 结果只保存候选，Agent 决定是否展示；需要有权者确认才会启用。

### 12.5 歧义与越权（FLOW-05）

- 两个人都叫小白：query 返回可见候选，明确 @ 后再执行。
- 乙说“我也叫临雀”：只更新乙的名称，不获得甲的资产与权限。
- 甲以真实当轮附件替明确可见的乙投稿：保存为乙的草稿，uploader 是甲；不替乙启用。
- 多人同批分别说名字：按每条证据作者分别更新，无法关联的内容不写入。
- 身份或授权缺失：人格解释需要哪一步，不泄露其他人的私有记录。

## 13. 逻辑数据模型与一致性

### 13.1 最小逻辑对象

以下是数据职责，不强制一对象一表，也不要求先造完整 ORM：

| 对象 | 必要字段／约束 |
| --- | --- |
| Person | UUID、类型 human/persona/character、控制者关联、当前修订、状态、创建时间 |
| AccountBinding | 平台命名空间、原生账号 ID、人物 UUID、验证来源；账号键唯一，模型不可直接写 |
| LegacyMapping | 原统一 user_id 与新 UUID 的兼容关联、迁移状态；有冲突不得假装唯一 |
| NameBinding | 人物、名称、类型、作用域、称呼／检索开关、来源和状态 |
| ProfileClaim | 人物、字段或陈述、来源类型、证据、适用范围、替代关系、状态 |
| VisualRevision | 视觉档案 ID、人物、不可变修订、外观／服装／推测说明、生命周期与当前指针 |
| Asset／ReferenceSet | 资产 ID、真实相对路径、格式／大小／哈希、来源父项；有序用途和必需项 |
| Evidence／Grant | 原消息索引、作者、范围、授权者、能力、有效期、撤回状态 |
| ChangeAudit | 操作者、动作、对象、预期及结果修订、幂等键、证据、时间与脱敏变更 |
| GenerationBinding | 已有 job_id 关联的输入清单、人物版本、grant、派生来源、上游提交边界及结果 |

长期身份和资料的权威元数据放入当前人格 SQLite 存储，扩展现有统一用户服务；不把人物身份真相分散放进多个 ToolDataStore。已有工具 JSON 队列继续保留任务执行职责。

### 13.2 文件组织建议（DATA-01）

```text
data/personas/<persona>/
├── persona.db                      # 扩展统一身份、名称、元数据和审计
├── assets/                         # 旧 self-only 扫描目录，兼容期不混入人类图片
├── visual_assets/
│   └── <person_uuid>/
│       ├── originals/              # 不可变原图
│       └── derived/                # 裁切、规范化、生成候选等
└── tool_data/
    └── artifacts/image_generate/   # 继续沿用的任务输入副本与成品
```

所有路径从显式 `work_path` 派生。数据库只存受控根内相对路径，读取时校验真实解析结果，防止软链接／重解析点与 `..` 越界。目录布局不是权限机制，不能代替对象授权。

### 13.3 并发、幂等与恢复（DATA-02）

- 新账号 UUID 使用唯一约束及事务创建，同一证据的重复更新返回相同变更结果。
- 可变指针使用预期修订 CAS，不能用“最新一条消息”无条件覆盖。
- 文件先安全物化、验证并原子落位，再提交可引用元数据；未完成文件不得标可用。
- SQLite 与现有 JSON 队列之间不宣称天然原子事务；采用有状态提交记录、稳定 job_id／幂等键和启动修复，能区分未提交、已入队、已外部提交及未知状态。
- 为防重复计费，启动恢复不得自动重放上游状态不明的生成；保留现有 running 中断失败边界或更严格状态。
- 自动配额预占、变更和审计必须与授权判断一致；并发请求不得超扣或突破限额。
- 文件清理按引用关系执行，不能用聊天缓存清理策略删除正式资产。

## 14. 兼容迁移与接入边界

### 14.1 统一身份迁移（MIG-01）

- 保留现有 `UnifiedUser.user_id` 及其被记忆、任务、关系引用的旧键，新增 UUID 兼容关联，不直接全量改主键。
- 正常旧用户增量分配稳定 UUID，支持 dry-run、统计、备份、可重复执行与回滚。
- 旧系统可能已有昵称回退误合并：发现同一旧记录存在无法验证的多个账号归属时列为待核查，不因迁移给每个账号自动共享其私人资产。
- 新入站解析修正为账号精确优先；姓名索引改为多候选视图，不延续单值覆盖造成的误合并。
- 历史记忆无法区分作者时标记来源不确定，不自动拆分或伪造历史身份。
- UUID 持久化后备份恢复及目录移动保持稳定；跨人格导入必须显式迁移，不默认互通。

### 14.2 旧参考图迁移（MIG-02）

- 旧人格目录扫描结果只能作为 self 资产迁移候选，不能证明所有图片真的属于人格。
- 由管理者确认归属、默认集与外观说明，再建立正式清单。
- 新用户图片绝不直接放进旧递归扫描树；兼容期继续允许旧路径手动参考，但不能声称具有人物编译保证。
- 清单可用后，正式人物分支以清单为准；旧路径提示可保留为兼容入口，不每轮加载全部新图库。
- 兼容期已排队旧任务保留原输入和 legacy 标记，但**新来源状态与范围规则优先于旧执行契约**。涉及已纳管素材的旧任务必须能回溯主体、修订、范围与素材状态；缺少绑定且无法验证的任务隔离待确认，不因取消逐人物手动 grant 就继续上传。旧任务不得自动变成人物正式资产。

## 16. 非功能需求与可观测性

### 16.1 性能与稳定性（NFR-01）

- 普通对话不新增强制 LLM、视觉请求或全库／全文件扫描；身份查询使用索引。
- 新身份库或资产模块不可用时，普通聊天仍可继续；涉及身份变更或正式人物生图时明确失败，不能为了可用性放弃权限检查。
- 验收基准建议：10,000 人物、50,000 条名称／资产元数据、暖缓存下，本地纯元数据 query 的 p95 ≤ 200ms；记录硬件与样本，不把外部 LLM 时间计入。
- 大文件入库和生图走异步 I/O；生图等待不长期持有用户回合锁，不以新增人物锁串行化不同群聊天。
- 文本资料摘要可保持确定性聚合；若用户明确要求深层经历检索，可使用既有检索能力，其延迟单独记录，不强行计入纯元数据 query 的 200ms 基准。
- 工具调用现有超时仍适用；网络导入不能在普通同步调用中逐张长时间等待，应返回可追踪任务或要求先完成导入。

### 16.2 安全（NFR-02）

- 所有模型输入均视为不可信；身份、作用域、路径、权限与预算必须由程序重验。
- 防任意文件读取、SSRF、超大／解码炸弹图片与重复生成；不信任扩展名或模型的“这是图片”声明。
- 新人物库不能成为原始聊天或私有图片的批量枚举接口。
- 授权只在服务侧判断；query 返回的 ID／句柄不是 bearer token。
- 纳入清单的受管资产及其候选、任务副本、关联成品，即使以原始路径传给旧 `read_image`、`image_generate` 或发送入口，也须识别为受管对象并复查对应能力；不能只保护新工具而让旧路径参数绕过。撤权后的回调只返回安全状态，不泄露可绕过权限的裸路径。
- 旧参数兼容是调用格式兼容，不保留越权读取／外传行为；普通非受管图片按既有策略处理。管理员、宿主机或高权限文件／命令工具的物理访问属于可信部署边界，本需求不宣称构成完整 OS 文件沙箱。
- 新生成的系统提示词保留现有安全尾部要求，工具结果不能覆盖系统策略。

### 16.3 观测与诊断（OBS-01）

最少记录并可按人物／任务／变更检索：

- 身份解析来源、候选数、歧义／误合并拦截、来源失效。
- 资料变更、修订冲突、授权拒绝及撤回。
- 资产缺失／损坏、编译耗时、参考序号与哈希、所选版本。
- 派生去重、配额预占／消耗／释放、上游提交与未知结果。
- 内部生成完成、正式启用、Agent 回调、平台外发回执分别统计。

普通日志不打印完整私有资料、原图字节、平台凭据或全部绝对路径。审计可追溯不等于把敏感内容广泛写日志。

### 17.1 验证方式

- 快速回归复用项目 `MockProvider`，无真实网络；断言最终图像请求的 prompt、图序与字节哈希。
- 使用临时工作目录模拟重启、并发、多群、缺图、撤权和迁移；不在真实用户数据上实验。
- 由子代理按上述对话场景执行操作与复核，主代理检查变更范围及最终差异。
- 有真实服务的双人效果测试需另获额度授权，与单元／业务回归分开，不作为自动测试隐式付费。
- 同域少量用例归并、相似情况参数化，单测目标 < 1 秒、全套目标 < 30 秒；不得为每条需求机械新建测试文件。
- 交付清理临时脚本、测试图片及无用候选，只保留正式测试夹具与约定产物。

每阶段完成还必须满足：

1. 业务场景验证、旧接口回归、迁移／回滚演练通过。
2. 文档明确区分该阶段已支持与后续未支持内容。
3. 新工具 Schema、管理配置、错误语义与示例同步到权威文档。
4. 有用户可见用法变化时更新项目说明；不将草案用法直接宣传为已可用。
5. 无真实账号、私有图片、密钥或临时测试产物进入版本库。

## 19. 待评审决策与已知风险

### 19.1 建议直接采用的基线

- UUID 在当前人格中持久化，账号精确优先，跨人格不自动共享。
- 一个 UUID 多名称，一个名称多候选；名称不是身份认证或授权。
- query 与写工具分离，人物库不承担全量记忆副本。
- 原图先保存，生成图默认候选，人物生图强制编译。
- 输入版本固定但权限动态复查；不把“生成完成”视为“已正式启用／已外发”。

### 19.2 上线前需确认的产品参数

| 决策 | 建议 | 未确认时行为 |
| --- | --- | --- |
| 人物资料能否在同人格跨群共享 | 由应用管理员明确扩大范围 | 保持来源会话范围，维护者也不自动扩群 |
| 自动派生预算承担者与次数 | 部署方设总额，用户仅能在额度内授权 | 无预授权不自动生成 |
| 自动补全推荐频率 | 使用第 15 节保守默认 | 不无限询问或自动补全 |
| 原图、候选与审计保留期 | 结合部署备份制度配置 | 上线前必须有可说明策略，不承诺彻底删除 |
| 管理 UI 优先级 | 工具闭环先行，后补可视化 | 使用受控管理入口，不手改数据库绕过审计 |
| 多账号本人验证与合并 | 后续单独设计 | 不自动合并；保持各账号独立 |

### 19.3 已知风险

- 单图到三视图包含未展示细节的设计补全，人工确认仍不可省略。
- 图像模型可能混淆多人或不遵循顺序；本需求可审计输入，不能用程序校验替代效果评估。
- 旧昵称回退可能已经污染身份映射，迁移不能自动修复全部历史归属。
- 模型可能漏调用人物工具或漏填 `subjects`；首版通过清晰 Schema、来源计划和错误反馈降低遗漏，不宣称完全理解所有自然语言。
- 当前工具分类是整工具粒度，未来开放纯自主付费生成需另行细化能力，不能通过简单改副作用标签解决。
- 外部接口提交、已发消息和备份都有撤回边界，必须向用户如实说明。
